# Verification status

This page records what has been verified, and on what. Until 2026-10-16 no Velocity development run (the overnight runs, the decisions run, the improvement run) had used a simulator, emulator or real device; device code was tested on the host against fake `adb`, WebDriverAgent, `devicectl` and usbmuxd. The web driver is tested against real headless Chrome on macOS.

**2026-10-25 device run.** On an Android 14 (API 34) arm64 emulator (`emulator-5554`, AVD `zii_arm64`) and two iOS 26.0 simulators (iPhone 17 Pro and iPhone 17, Xcode 26.0.1 build 17A400), all on one Apple Silicon Mac, these ran:

- `tests/smoke/android-settings.yaml` and `tests/smoke/ios-settings.yaml`;
- a private real-world app suite (17 tests, React Native) on the iPhone 17 Pro;
- the VelocityLab suites (a separate test app with the same screens on both platforms): 34 Android tests and 15 iOS tests, the iOS ones on WebDriverAgent and on VelocityRunner with `ios.verifyTap`;
- throwaway suites checking that a crash, a killed app, ambiguous healing, a tap under the keyboard and an out-of-range shard all fail;
- `velocity mcp` over stdio and the `velocity inspect` HTTP API on the emulator.

Later that day each feature track (AI providers, MCP tasks, failure evidence, `init`/`doctor`, `explore`, the console) checked its own work on the same devices, and the merged build was checked again (the **integration run** below). The table keeps the latest result for each area.

Real iPhones and Android hardware were not used. "Host only" means tested against fakes or mock servers on this Mac, never on a device.

### Found and fixed by the 2026-10-25 run

- **DV-1** (MCP): `wait_for_element`, `tap`, `type_text`, `get_element` and `assert_visible` read the driver's 2 s tree cache, so after a tap they saw the tree read mid-transition (`wait_for_element` took 2.2 s for a page that was up in 0.7 s). Tool lookups now read the live screen.
- **DV-2** (iOS, WDA): a new session launched the app before Velocity turned WDA's idle wait off, so WDA waited up to 10 s for the app to go quiet. `shouldWaitForQuiescence: false` now goes with the session and with `/wda/apps/launch` (session start 2.5 s → 1.65 s for Settings).
- **DV-3** (iOS simulators): an app without the in-app sync probe waited out the 2.5 s probe grace on every `launchApp`. It is waited out once per run now.
- **DV-4** (`ios.verifyTap`): SwiftUI apps on iOS 26 keep an empty full-screen window after the content window. When XCTest's own element couldn't be placed (an alert's button), that window's root was taken as drawn over the target. An empty other window is now looked through.
- **DV-5** (`ios.verifyTap`): a `WKWebView` page is drawn by WebKit's WebContent process, so every tap into a web view was refused as "another process draws". Inside a web view that process counts as the app.
- Suites: `tests/smoke/android-settings.yaml` checked a word that also matched the home screen (`textContains` ignores case); the private real-world app suite typed the OTP into a placeholder (text selectors don't read placeholders) and one test skipped the guest card.
